# 原型（Prototype）

原型是**用来回答一个问题的、一次性代码**。问题是什么，原型的形态就跟着变。

## 选择分支

先确认要回答的是哪个问题——从用户的话、周边代码判断，用户在场时可以直接问：

- **「这段逻辑 / 状态模型感觉对不对？」** → 走下列「逻辑原型」章节。产物是**一个可分享的单 HTML 文件**——自由点按按钮 + 分标签的引导走查，把状态机推过那些在纸面上很难想清楚的场景，而且非开发人员也能上手驱动。
- **「这东西应该长什么样？」** → 走下列「UI 原型」章节。在**同一条路由**上生成几套**结构上差异巨大**的 UI 变体，通过 URL 查询参数和一个底部悬浮条切换。

两个分支产出的产物完全不同——选错了就等于整个原型白做。如果问题确实含糊、用户又联系不上，就默认选更贴合周边代码的那一支（后端模块 → 逻辑；页面或组件 → UI），并把这一假设写在原型最上面。

## 两个分支通用的规则

1. **从第一天起就当它是抛弃品，并明确标注。** 把原型代码放在它将来真正会用到的地方旁边（紧挨着它要原型化的模块或页面），让上下文一目了然——但命名要让随便一读的人都能看出它是原型、不是生产代码。对一次性 UI 路由，遵守项目已有的路由约定，不要凭空发明新的顶层结构。
2. **跑起来要零门槛。** UI 原型用项目任务运行器里的一条命令启动（`pnpm <name>`、`python <path>`、`bun <path>` 等）。逻辑演示就是用户双击打开的一个 HTML 文件。无论哪种，启动它都不需要动脑子。
3. **默认不持久化。** 状态放在内存里。持久化恰恰是原型要 *检验* 的东西，而不是原型应该依赖的东西。如果问题本身就涉及数据库，就打到临时数据库或本地文件上，并起一个一目了然的名字（如「PROTOTYPE — 用后即删」）。
4. **跳过打磨。** 不写测试、不做超出「让原型跑得起来」这一范围的错误处理、不抽抽象。目的是快速学到东西。
5. **把状态摆出来。** 每次动作之后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到发生了什么变化。
6. **做完就归档。** 把验证通过的决策折入真实代码，然后把原型本身作为**一手材料**归档：提交到一个独立于主干的抛弃分支上，在实现 issue 里留一个指向该分支的上下文指针。答案本身也要记下来——结论以及它解决的那个问题——写进 issue 或提交信息里。主线只保留验证通过的决策。

# 逻辑原型（LOGIC）

一个**自包含的单 HTML 文件**——一个**可分享的演示**——让任何人通过点击按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态转换或数据形态**时用它——就是那种纸面上看着合理、一旦拿真实用例跑一遍立刻觉得不对劲的东西。

因为它是单文件、免安装，你可以直接交给非开发人员——设计师、产品经理、领域专家——让他们亲手感受这个模型。所以它要说他们的话，而不是代码的话。

## 何时该用这个形态

- 「我不确定这个状态机能不能处理『先 X 再 Y』这种边界情况。」
- 「这个数据模型到底能不能表示这种…… 的情况？」
- 「我想在动手写之前，先把 API 该长什么样摸清楚。」
- 任何「想点按钮、看状态变化」的需求。

如果问题是「这东西应该长啥样」——走错分支了，改用上面「UI 原型」章节。

## 流程

### 1. 把问题写清楚

动手写代码之前，先写下一段话：你在原型化的是哪个状态模型、要回答的是什么问题。放在演示最上面的可见引言里，而不是只写进注释。一个答错问题的逻辑原型是纯浪费——把问题摆明，之后随时能核对，无论用户此刻在场还是日后回来看。

### 2. 把逻辑隔离进一个可移植模块

把真正的逻辑——也就是回答问题的那个部分——放进一个单独的 `<script>` 块，写成一个小的、纯的模块，将来能直接拎出去、丢进真实代码库。它周围的页面是一次性的，这个模块不是。

正确的形态取决于问题：

- **纯 reducer** —— `(state, action) => state`。适合动作是离散事件、状态是单一值的情况。
- **状态机** —— 显式的状态和转换。适合「当前到底哪些动作是合法的」本身就是问题的一部分时。
- **一组作用于普通数据类型的纯函数**。适合没有隐含当前状态、只有纯变换的情况。
- **一个方法面清晰的类或模块**。适合逻辑确实持有持续内部状态的情况。

选最贴合所问问题的那个形态，而不是最方便接页面的那个。保持纯粹：不碰 DOM、不碰 `document`、不让按钮处理器伸进它内部。页面调用它，方向不能反过来。这正是让原型活得比它自己更久的理由：问题一答完，验证过的 reducer / 状态机 / 函数集就能原样提升进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS——不用框架、不打包、不起服务，全部内联，双击就能打开、邮件来回发也不散架。任何人打开就能跑。

为**非开发人员**而写。每个标签都用**领域语言**而不是代码——按钮和状态读起来像业务，不像 reducer。用大白话解释正在发生什么。

自上而下排一个干净的层级：

1. **标题 + 一句话说明**，讲清这个演示能让你探索什么（就是第 1 步的那个问题）。
2. **当前状态** —— 完整相关状态，渲染成一个可读面板（有标签的字段，不是裸 JSON 堆），每次点击后重渲染，让变化可见。在能帮助非开发人员跟上时，点明「刚刚变了什么」。
3. **自由点按按钮** —— 每个动作一个按钮，始终可用，任何人都能按任意顺序拨弄模型。每次点击派发对应动作并重渲染状态。
4. **引导走查** —— 一组**场景**，每个场景一个标签页。每个标签页里放一段简短的平实描述——它搭建的情境、要观察什么——下面就是该场景**要按的按钮顺序**。每一步都是一个真按钮：点击即执行该动作并切到下一步。开始走查时重置到已知初始状态，让场景每次跑出来都一样。

选的场景要演示那些别扭的情况——快乐路径、一个棘手的边界、一次本应非法的尝试——正是纸面上难想清楚的那些。

保持漂亮但有节制：干净排版、留白充足、单一强调色。不加动画、不玩花样——不让任何东西跟状态和按钮抢戏。

### 4. 交接出去

把文件发给他们，或替他们打开。他们会顺着走查和自由点按一路点下去；真正有意思的时刻是他们说「等等，这不应该能发生」或「咦，我以为 X 会不一样」——那正是*想法*里的 bug，也正是这件事的全部意义。他们想要新动作或新场景，就加。原型会演化。

### 5. 归档答案与原型

原型一旦答完它的问题，先记下答案，再按上文「通用规则」第 6 条的方式归档原型。逻辑这一支的具体对应：验证过的 reducer / 状态机 / 函数集提升进真实模块（决策被吸收）；HTML 外壳随行落到那个把原型当一手材料保留的抛弃分支上——它是自包含单文件，在那里依然能随时重新跑起来。

## 反模式

- **别加测试。** 一个需要测试的原型，就不再是原型了。
- **别接真实数据库。** 除非问题就是关于持久化的，否则用内存状态。
- **别做抽象腾挪。** 别想「以后要是支持 X 呢」。原型只回答一个问题。
- **别把逻辑和页面糊在一起。** 纯模块一旦引用 DOM、`document` 或按钮处理器，就不再有可提升性。保持页面只是纯模块之上的一层薄壳。
- **别上框架、打包器或服务器。** 一个接收方双击即开的文件；React 应用或开发服务器会废掉「可分享」这件事。
- **别把 HTML 外壳送进生产。** 页面是为让人手点而优化的；它背后的逻辑模块才是值得留下的那部分。

# UI 原型（UI）

在**同一条路由**上生成**几套结构上差异巨大**的 UI 变体，通过一个底部悬浮条切换。用户在浏览器里翻转变体，挑一个（或从每个里各偷一点），然后把其余全部丢掉。

如果问题是关于逻辑/状态而不是长相——走错分支了，改用上面「逻辑原型」章节。

## 何时该用这个形态

- 「这个页面该长什么样？」
- 「定稿前我想看看这个仪表盘的几个方案。」
- 「试试给设置页换个布局。」
- 任何用户本会花一整天在脑子里三个模糊线框之间犹豫不决的情形。

## 两个子形态——强烈优先子形态 A

当 UI 原型**贴着应用其余部分**时——真实的头部、真实的侧栏、真实的数据、真实的密度——才最好判断。一条孤零零的一次性路由是真空：每个变体单看都不错。只要存在合理可承载的现有页面，就默认子形态 A。只有当原型真的没有就近落脚处时，才退到子形态 B。

### 子形态 A —— 对现有页面做调整（首选）

路由已存在。变体渲染在**同一条路由**上，由 `?variant=` 这个 URL 查询参数门控。既有的数据获取、参数、鉴权全部保留——只有渲染结果在换。这是默认选项；没有具体理由就别换。

如果原型对象是某个还没有页面、但*天然该住在某页里*的东西（仪表盘的新区块、设置页的新卡片、现有流程里的新步骤）——这仍是子形态 A。把变体挂载进宿主页面即可。

### 子形态 B —— 新建页面（最后手段）

只有当被原型化的东西真的没有现成页面可住时才用它——例如一个全新的顶层界面，或一个无法合理嵌入任何地方的流程。

按项目已有的路由约定建一条**一次性路由**，别发明新的顶层结构。命名要一眼看出是原型（例如路径或文件名里带 `prototype` 这个词）。同样沿用 `?variant=` 模式。

在落到子形态 B 之前先自检：是真的没有可嵌入的现有页面吗？空路由会藏起那些被填满的页面会暴露出来的设计问题。

两种子形态的底部悬浮条完全一致。

## 流程

### 1. 写清问题并定下 N

默认 **3 套变体**。超过 5 套就不再是「差异巨大」，开始变成噪音——到 5 封顶。

把计划用一句话写下来，放在原型所在处或文件顶部注释里：

> 「设置页的三套变体，通过 `?variant=` 切换，复用现有的 `/settings` 路由。」

无论用户在场反驳还是不看，这句话都有用。

### 2. 生成结构上差异巨大的变体

草拟每一套变体。每套都要守：

- 页面的用途以及它能拿到什么数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，是什么用什么）。
- 一个清晰的导出组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同的布局、不同的信息层级、不同的首要操作，而不是仅仅换个配色。三张微调过的卡片网格不叫 UI 原型，叫贴壁纸。要是两版草稿太像，就明确用「不许用卡片网格」重新做其中一版。

### 3. 把它们接起来

在路由上建一个切换器组件（伪代码，按项目框架适配）：

```
const variant = searchParams.get('variant') ?? 'A';
// 变体 = 'A' 时渲染 VariantA，'B' 时渲染 VariantB，'C' 时渲染 VariantC
// 再挂一个 PrototypeSwitcher（变体列表 + 当前值）
```

子形态 A（现有页面）：把既有的数据获取全部放在切换器之上；每次换变体只换渲染出的子树。

子形态 B（新建页面）：一次性路由挂载同一个切换器。

### 4. 建底部悬浮切换器

屏幕底部居中的一个固定定位小条，含三样东西：

- **左箭头** —— 切到上一个变体（循环回绕）。
- **变体标签** —— 显示当前变体键；若该变体导出了名称，也一并显示。如 `B — 侧栏布局`。
- **右箭头** —— 切到下一个（循环回绕）。

行为：

- 点箭头即更新 URL 查询参数（走框架路由，如 Next 的 `router.replace`、React Router 的 `navigate` 等），让当前变体可分享、刷新后不丢。
- 键盘：`←` 与 `→` 方向键也能循环切换。当焦点落在 `<input>`、`<textarea>` 或 `[contenteditable]` 里时，不拦截方向键。
- 视觉上与页面明显区分（如高对比胶囊、轻微阴影），一看就知道它不是被评估的设计的一部分。
- 生产构建里隐藏——用环境判断（如非生产环境才渲染）把关，别让一次手滑的原型合入把悬浮条带给了用户。

把切换器做成单一共享组件，让两种子形态都能复用。放在项目里共享 UI 该在的地方。

### 5. 交接出去

把 URL（以及 `?variant=` 各键）亮出来。用户会随时翻看。真正有意思的反馈通常是**「我想要 B 的头部 + C 的侧栏」**——那才是他们真正想要的设计。

### 6. 归档答案并清理

某个变体胜出后，先记下答案——是哪个变体、为什么——再按上文「通用规则」第 6 条归档原型。把胜者折进真实代码，其余搬到抛弃分支，而不是进主线：

- **子形态 A** —— 把胜者折进现有页面；失败的变体和切换器从主线移除。
- **子形态 B** —— 把胜出的变体扶正为真实路由；一次性路由和切换器从主线移除。

整套变体是一手材料，所以它们落进抛弃分支，而不是垃圾桶——留在主线里的变体组件和切换器腐化得飞快，还会把下一位读者搞晕。

## 反模式

- **只是配色或文案不同的变体。** 那是微调，不是原型。真正的变体要在结构上意见相左。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了本意。每个变体都应有权把布局整个扔掉。
- **把变体接到真实写操作上。** 只读原型就够。某个变体若需要写入，就接到桩上——问题是「这东西长啥样」，不是「后端能不能跑」。
- **把原型直接扶正进生产。** 变体代码是在原型约束（不写测试、错误处理最简）下写的。折入时要按规范重写。
