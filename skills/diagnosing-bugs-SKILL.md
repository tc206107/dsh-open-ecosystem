# 诊断 Bug

一套面向「硬 bug」的纪律。只有在明确给出理由时才允许跳过阶段。

探索代码库时，先读 `CONTEXT.md`（若存在）以建立相关模块的心智模型，并查看所触及区域的 ADR 记录。

## 脱敏

本 skill 会要求你展示命令、输出与捕获的产物。**先脱敏每一个密钥**——用 `<REDACTED>` 占位。把循环构建在环境变量之上，让凭据留在环境中而非出现在你所展示的内容里。捕获的产物常携带鉴权请求头：只引用携带信号的那几行。

若脱敏后的输出不足以诊断 bug，直接说明并提出向用户索取。

## 阶段一 —— 构建反馈环

**这才是本 skill 的核心。** 其余都是机械步骤。只要你对这个 bug 有一个 **tight** 的通过/失败信号——一个能在「这个 bug」上报红（goes red）的信号——你就一定能找到根因；二分、假设检验、仪器化都只是消费这个信号而已。没有这个信号，盯着代码看多久都没用。

在这一步投入不成比例的精力。**主动、有创造力、拒绝放弃。**

### 构建反馈环的途径 —— 大致按此顺序尝试

1. **失败测试（failing test）**：在能触达该 bug 的任意 **seam 接缝** 处写测试——单元、集成或端到端。
2. **Curl / HTTP 脚本**：对运行中的开发服务器发请求。
3. **CLI 调用**：喂入夹具输入，将 stdout 与已知正确快照比对差异。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，对 DOM / console / network 做断言。
5. **回放捕获的 trace**：把一次真实的网络请求 / 载荷 / 事件日志存盘，在隔离状态下重放该代码路径。
6. **一次性 harness**：起一个最小系统子集（单个服务 + 模拟依赖），用一次函数调用即可触发该 bug 代码路径。
7. **属性 / 模糊循环（fuzz）**：若 bug 是「偶发错误输出」，跑 1000 个随机输入，找出失败模式。
8. **二分（bisection）harness**：若 bug 出现在两个已知状态（提交、数据集、版本）之间，自动化「在状态 X 启动、检查、重复」，以便用 `git bisect run` 跑通。
9. **差分循环（differential）**：同一输入分别喂给旧版与新版（或两种配置），比对输出差异。
10. **人机协同（HITL）脚本**：最后手段。若必须由人点击，用 `scripts/hitl-loop.template.sh` 驱动他们，让循环仍保持结构化；捕获的输出回传给你。

构建出正确的反馈环，bug 就修复了 90%。

### 收紧（tighten）反馈环

把反馈环当成一个产品。一旦有了「一个」循环，就 **收紧** 它：

- 能不能更快？（缓存初始化、跳过无关启动、缩小测试范围。）
- 能不能让信号更锐利？（断言具体症状，而不是「没崩溃」。）
- 能不能更确定？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

一个 30 秒的不稳定循环几乎等于没有循环；一个 2 秒的确定性循环才是 tight——这是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发跑 100 遍、并行化、加压、缩小时间窗口、注入 sleep。50% 复现率的 flaky bug 可调试；1% 不可调——持续抬高复现率直到可调试。

### 当确实无法构建反馈环

停下来并明确说明。列出你尝试过的一切。向用户索取：(a) 能复现该问题的环境访问权；(b) 一份脱敏后的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏）；或 (c) 授权添加临时生产仪器化。**在没有反馈环的情况下，不要进入假设阶段。**

### 完成标准 —— 一个能报红的 tight 反馈环

当反馈环 **tight** 且 **可报红（red-capable）** 时阶段一完成：你能准确说出**一条命令**——一个脚本路径、一次测试调用、一条 curl——而且你**至少已经跑过一次**（展示调用与其输出，已脱敏），同时满足：

- [ ] **可报红** —— 它驱动真实的 bug 代码路径，并断言**用户描述的确切症状**，因此能在此 bug 上变红、修复后变绿。不是「运行无报错」——它必须能 _抓住这个具体的 bug_。
- [ ] **确定** —— 每次运行得到同一结论（flaky bug 按上文固定一个高复现率）。
- [ ] **快** —— 以秒计，而非分钟。
- [ ] **可无人值守运行** —— 你能无人值守地跑它；仅通过 `scripts/hitl-loop.template.sh` 才引入人在环。

若你发现自己开始读代码去建立理论、而这条命令还不存在，**立刻停下——直接跳到假设正是本 skill 要防止的失败。** 没有可报红的命令，就没有阶段二。

## 阶段二 —— 复现并最小化

运行反馈环。看着它报红——bug 出现了。

确认：

- [ ] 反馈环产生的是**用户**描述的失败模式——而非恰好相邻的另一种失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行间可复现（或对非确定性 bug，复现率高到足以作为调试靶子）。
- [ ] 你已捕获确切症状（错误消息、错误输出、缓慢计时），以便后续阶段验证修复确实命中它。

### 最小化

一旦报红，就把复现缩到**仍能报红的最小场景**。**逐项**裁减输入、调用方、配置、数据与步骤，每裁一项重跑一次反馈环——只保留对该失败「承载受力（load-bearing）」的东西。

这么做的价值：最小复现缩小了阶段三的假设空间（可怀疑的移动部件变少），并在阶段五成为干净的回归测试。

完成标准：**每个剩余元素都是承载受力的**——去掉其中任何一个都会让反馈环变绿。

在**复现并最小化**之前，不要继续。

## 阶段三 —— 提出假设

在测试任何一个之前，先生成 **3–5 个排序假设**。只生成一个假设会锚定在第一个貌似合理的想法上。

每个假设必须**可证伪**：写明它所预测的结果。

> 格式：「若 <X> 是根因，则 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。」

若你无法写出预测，这个假设只是「感觉」，丢弃或锐化它。

**在测试前把排序列表展示给用户。** 他们常有领域知识能瞬间重排（「我们刚对 #3 部署了一个改动」），或知道哪些假设已经被排除。这是低成本的检查点，却能省大量时间。不要阻塞于此——若用户不在场，按你的排序继续。

## 阶段四 —— 仪器化

每个探针必须对应阶段三里的某个具体预测。**每次只改变一个变量。**

工具优先级：

1. **调试器 / REPL 检查**（环境支持时）。一个断点胜过十条日志。
2. **定向日志**，打在能区分各假设的边界上。
3. 绝不「全量打日志再 grep」。

**给每条调试日志打唯一前缀标签**，例如 `[DEBUG-a4f2]`。收尾时的一次 grep 即可清理。无标签的日志留下，有标签的日志死掉。

**性能分支。** 对性能回退，日志通常是错的。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），再二分定位。先测量，后修复。

## 阶段五 —— 修复 + 回归测试

在修复**之前**先写回归测试——但仅当存在**正确的 seam 接缝**时才写。

正确的 seam 是：测试能在**真实的调用点**复现**真实的 bug 模式**。若唯一可用的 seam 太浅（bug 需要多个调用方、而这里只有单调用方测试；或单元测试无法复现当初触发 bug 的调用链），在此写回归测试只会给人虚假信心。

**若不存在正确的 seam，这本身就是发现。** 把它记下来。代码库架构正在阻止这个 bug 被锁定，在下一阶段标记出来。

若存在正确的 seam：

1. 把最小化后的复现变成该 seam 处的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 用原始（未最小化）场景重跑阶段一的反馈环。

## 阶段六 —— 清理 + 复盘

宣告完成前的必查项：

- [ ] 原始复现不再复现（重跑阶段一反馈环）
- [ ] 回归测试通过（或 seam 缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 仪器化已移除（用前缀 grep）
- [ ] 一次性原型已删除（或移入明确标注的调试位置）
- [ ] 被证实正确的假设已写入提交 / PR 消息——让下一位调试者受益

**然后问：什么本可以预防这个 bug？** 若答案涉及架构性改动（没有好的测试 seam、纠缠的调用方、隐藏的耦合），把这些具体信息交给「运行 /improve-codebase-architecture skill」。在修复**完成之后**再做此建议，而非之前——此刻你比开始时掌握了更多信息。

### 深模块备注

在寻找 seam 与探针边界时，优先在**深模块（deep module）**处下手：这些模块接口窄而内部隐蔽复杂，跨越它们的边界处能提供最锐利的观测点；避免在大量浅模块的薄接口间分散精力，那些地方信号会被稀释。
