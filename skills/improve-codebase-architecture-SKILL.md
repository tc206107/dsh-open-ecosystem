# 改进代码库架构

找出架构摩擦点，并提出**深化机会（deepening opportunities）**——即把浅模块重构为深模块的重构建议。目标是可测试性与 AI 可导航性（navigability）。

本技能由项目的领域模型驱动，并建立在一套共享设计词汇之上：

- 运行 `/codebase-design` 技能以获取架构词汇（**module 模块**、**interface 接口**、**depth 深度**、**seam 接缝**、**adapter 适配器**、**leverage 杠杆**、**locality 局部性**）及其原则（删除测试、「接口即测试面」、「一个适配器 = 假设性接缝，两个 = 真实接缝」）。在每一条建议中都要精确使用这些术语——不要滑向「component 组件」「service 服务」「API」或「boundary 边界」等说法。
- `CONTEXT.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录本技能不应重复争论的决策。

## 流程

### 1. 探索

**先定范围再扫描——YAGNI。** 深化一个模块的回报在于让未来对它的改动更容易，所以要格外重视代码库中近期频繁变动的部分。在动工之前先决定*看哪里*：

- 如果用户指明了方向——某个模块、子系统或痛点——直接采用它，跳过下面的推断。
- 否则，往回翻一段足够的提交历史（`git log --oneline`）找出代码库的热点——反复出现的文件与区域——让这些路径优先吸引你的注意力。如果改动分散、没有明显热点，就扩大范围。

先读项目的领域词汇表（`CONTEXT.md`）以及你即将触及区域的任何 ADR。

然后派一个子代理去遍历代码库。不要死守固定启发式——有机地探索，并记下你体验到的摩擦感：

- 哪里理解一个概念需要在许多小模块之间来回跳转？
- 哪些模块是**浅层（shallow）**的——接口复杂度和实现几乎相当？
- 哪里为可测试性抽取了纯函数，但真正的 bug 藏在它们的调用方式里（缺乏**局部性 locality**）？
- 哪里紧耦合的模块跨越接缝相互泄漏？
- 代码库的哪些部分未被测试，或难以通过当前接口测试？

对任何你怀疑是浅层的东西应用**删除测试（deletion test）**：删掉它会集中复杂度，还是仅仅转移复杂度？「会集中」正是你要找的信号。

### 2. 以 HTML 报告呈现候选

生成一个自包含的 HTML 文件写入系统临时目录，避免任何产物落入仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），写到 `<临时目录>/architecture-review-<时间戳>.html`，确保每次运行拿到一个新文件。为用户打开它——Linux 用 `xdg-open <路径>`、macOS 用 `open <路径>`、Windows 用 `start <路径>`——并告知其绝对路径。

报告使用 **CDN 引入的 Tailwind** 做布局与样式，**CDN 引入的 Mermaid** 画那些能可靠表达结构的图（图/流程/时序）。交替使用 Mermaid 与手写 CSS/SVG 视觉——当关系是图形状的（调用图、依赖、时序）用 Mermaid，当你想更编辑化时（体量图、剖面图、折叠动画）用手工 div/SVG。每个候选给一个**前后对比可视化**。要视觉化。

为每个候选渲染一张卡片，包含：

- **文件**——涉及哪些文件/模块
- **问题**——为什么当前架构造成摩擦
- **解法**——用平实语言描述什么会改变
- **收益**——以局部性与杠杆，以及测试如何改善来解释
- **前后对比图**——并排、手绘，说明浅层状态与深化之后
- **推荐强度**——`Strong 强烈`、`Worth exploring 值得探索`、`Speculative 推测性` 三者之一，渲染为徽章

报告结尾放一个**首选推荐（Top recommendation）**区块：你会最先处理哪个候选，以及为什么。

**领域用 `CONTEXT.md` 词汇，架构用 `/codebase-design` 词汇。** 若 `CONTEXT.md` 定义了「Order」，就说「Order 接单模块」——而不是「FooBarHandler」，也不是「Order service」。

**ADR 冲突**：若某个候选与既有 ADR 相抵触，只有在摩擦真实到值得重新审视该 ADR 时才呈现。在卡片中清楚标注（例如警示标注：_"与 ADR-0007 相抵触——但值得重新开启，因为……"_）。不要罗列 ADR 禁止的每一条理论重构。

#### 报告页面结构要点

- **脚手架**：`<!doctype html>`、`<meta charset="utf-8">`，标题「架构评审——{仓库名}」。头部引入 Tailwind CDN 与 Mermaid ESM 导入，另加一小段自定义 CSS 处理 Tailwind 覆盖不到的部分（虚线接缝线、手绘箭头、深模块渐变背景）。
- **页头**：仓库名、日期，以及一段紧凑图例：实线框 = 模块，虚线 = 接缝，红色箭头 = 泄漏，粗深色框 = 深模块。不要写介绍段落——直接进入候选。
- **候选卡片**：每张卡片一个 `<article>`。标题简短、点名深化（如「折叠 Order 接单管线」）；徽章行放推荐强度（Strong = 翠绿、Worth exploring = 琥珀、Speculative = 石板灰）加一个依赖类别标签（`in-process`、`local-substitutable`、`ports & adapters`、`mock`）；文件列表用等宽字体；**前后对比图**是核心，两列并排；问题一句话、解法一句话；收益用点列出、每点 ≤6 字；ADR 警示（如适用）一行、琥珀色框。
- **图样式**：按候选选型并混用，别让每张图长一样。依赖/调用流用 Mermaid `flowchart`/`graph`，用 `classDef` 把泄漏边染红、深模块染深；Mermaid 布局不配合时用手工框-箭头（绝对定位的 SVG 线）；分层浅层用剖面图（横向条带）；「接口和实现一样宽」用体量图（接口矩形与实现矩形并排，浅层时几乎等高，深化后接口矮、实现高）；调用树「折叠」用调用图坍缩（嵌套框 → 单个框，内部调用淡显其中）。
- **样式纪律**：编辑化而非仪表盘风；留白充足；颜色克制（一个主色加红色泄漏、琥珀警示）；图约 320px 高以并排；模块标签用 `text-xs uppercase tracking-wider`；脚本仅 Tailwind CDN 与 Mermaid ESM，其余静态。
- **首选推荐区块**：一张更大的卡片——候选名、一句理由、指向其卡片的锚点链接。仅此而已。
- **术语纪律**：精确使用 module/interface/implementation/depth/deep/shallow/seam/adapter/leverage/locality；**禁止**用 component、service、unit（替代 module）、API/signature（替代 interface）、boundary（替代 seam）、layer/wrapper（替代 module）。收益点用词汇表命名收益（如「局部性：bug 集中到一个模块」「杠杆：一个接口 N 个调用点」「接口缩小；实现吸收包装层」），不要写「更易维护」「代码更干净」。不犹豫、无铺陈、删掉「值得注意的是……」；能成点列就成点列，能删的点就删，术语不在词汇表里就先找词汇表内更贴切的，再斟酌自造。

在文件写好之前**不要**提议任何具体接口。文件写好后问用户：「这些里面你想探索哪一个？」

### 3. 盘问循环

用户选定一个候选后，运行 `/grilling` 技能陪他走决策树——约束、依赖、深化后模块的形状、接缝背后藏着什么、哪些测试能存活。

随着决策逐步明晰，副作用即时落地——运行 `/domain-modeling` 技能保持领域模型同步更新：

- **把深化后的模块命名为 `CONTEXT.md` 里没有的概念？** 把该术语加进 `CONTEXT.md`。文件不存在就惰性创建。
- **对话中把一个模糊术语澄清了？** 当场更新 `CONTEXT.md`。
- **用户以站得住脚的理由否决了候选？** 提议一份 ADR，措辞为：_"要我把它记为 ADR，好让未来的架构评审不再重复建议它吗？"_ 只有当该理由确实是未来探索者避免重复建议所需时才提议——跳过临时理由（「现在不值当」）和不言自明的理由。
- **想为深化后的模块探索备选接口？** 运行 `/codebase-design` 技能，使用其「设计两次」并行子代理模式。
