# 测试驱动开发

TDD 就是 red 循环——红灯→绿灯。本技能是本循环产出"值得保留的测试"的参照：什么才是好测试、测试写在哪、反模式有哪些、以及 red 循环的规则。每一节都适用于每一个循环——要在进入循环之前和循环进行之中反复查阅，而不是事后才看。

探索代码库时，先读 `CONTEXT.md`（如果存在），让测试命名和接口用词与项目的领域语言保持一致；同时尊重你所改动区域的 ADR 决策。

## 什么才是好测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以整个重写，测试却不应跟着改。好测试读起来像一份规格说明——"用户能用有效购物车结账"直接告诉你存在哪项能力——并且能扛过重构，因为它不关心内部结构。

## Seam 接缝——测试写在哪

**seam 接缝**是你做测试所面对的公共边界：始终在接缝观察行为，从不伸进内部。测试落在接缝上，绝不针对内部实现。

**只在预先约定的 seam 接缝上测试。** 在写任何测试之前，先写下被测的接缝，并与用户确认。不经确认的接缝不写任何测试。你不可能测遍一切——提前约定接缝，正是让测试投入落在关键路径和复杂逻辑上，而不是落在每一个边界情形上。

先问："公共接口是什么？我们应该测试哪些接缝？"

当接口本身的形态存疑时——模块该有多深、接缝该放在哪、接口该暴露什么——运行 /codebase-design skill，借用它的术语词汇表。它是 module（模块）、interface（接口）、depth（深度）、seam（接缝）、adapter（适配器）、leverage（杠杆）与 locality（局部性）这些术语的唯一来源，是一份要在写作中查阅的参照，而不是一次要跑通的会话。

## 反模式

- **与实现耦合**——mock 了内部协作者、测试了私有方法、或通过旁路信道验证（查数据库而不走接口）。判断标志：行为没变，测试却在重构时崩了。
- **同义反复**——断言用代码自身的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、以同样方式手工推导的快照、断言常量等于它自己），于是测试靠构造恒成立，永远不可能与代码产生分歧。期望值必须来自独立的真值来源——一个已知正确的字面量、一个演算过的例子、规格说明。
- **水平切片**——先写完全部测试，再写完全部实现。批量测试验证的是*想象中*的行为：你测的是事物的*形状*而非用户可见的行为，测试对真实变化失去敏感度，而且你在理解实现之前就锁死了测试结构。改用**垂直切片**——一个测试 → 一个实现 → 循环往复，每个测试都是一颗 tracer bullet（示踪弹），回应着上一轮循环教给你的东西。

## red 循环的规则

- **绿灯之前必有红灯。** 先写会失败的测试，再写刚好让它通过的最少代码。不预判未来的测试，也不添加投机性功能。
- **一次只做一个垂直切片。** 每轮循环只做一个接缝、一个测试、一个最小实现。
- **重构不属于本循环。** 重构属于评审阶段（运行 /code-review skill），而不是红灯→绿灯的实现循环。
