对 `HEAD` 与用户给定固定点之间的 diff 做双轴审查：

- **Standards 标准轴** —— 代码是否符合本仓库文档化的编码标准？
- **Spec 规格轴** —— 代码是否忠实实现了原始的 issue / 规格？

两条轴各自以**并行子智能体**运行，互不污染彼此的上下文，随后由本技能汇总二者的发现。

issue 追踪器应由环境提供；若 `docs/agents/issue-tracker.md` 缺失，请运行「/setup-matt-pocock-skills skill」补全。

## 流程

### 1. 锁定固定点

用户所说的任何东西都是固定点——提交 SHA、分支名、标签、`main`、`HEAD~5` 等。若用户没有指定，请先询问。

一次性记下 diff 命令：`git diff <fixed-point>...HEAD`（三点，使比较基于 merge-base）。同时用 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

在继续之前，确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。坏引用或空 diff 应在此处失败——而不是在两个并行子智能体内失败。

**完成标准**：固定点已解析；diff 非空；diff 命令与提交列表已作为文字记录，可直接粘贴给子智能体。

### 2. 定位规格来源

按以下顺序寻找原始规格：

1. 提交信息中的 issue 引用（`#123`、`Closes #45` 等）——通过 `docs/agents/issue-tracker.md` 中的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或特性匹配的规格文件。
4. 若都未找到，询问用户规格在哪里。若确认没有规格，**Spec** 子智能体跳过并在最终报告中标注"无可用规格"。

**完成标准**：已得到一个规格来源的路径或已获取的规格内容；或已确认无规格并记录该结论。

### 3. 识别标准来源

仓库中任何记载代码应如何编写的文档均可作为来源，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库自身文档之外，Standards 轴始终携带下方的 **smell 基线**——一组固定的 Fowler 代码坏味（《重构》第 3 章），即使仓库什么也没记载也仍然适用。有两条规则约束它：

- **仓库文档优先。** 已文档化的仓库标准始终胜出；当它认可了基线会标记的某个做法时，抑制该坏味。
- **始终是判断而非硬违规。** 每条坏味都是带标签的启发式（"可能是 Feature Envy"），从来不是硬性违规——并且与这里的任何标准一样，跳过工具链已经强制检查的内容。

每条坏味读作 *是什么* → *如何修*；将它与 diff 一一比对：

- **神秘命名（Mysterious Name）** —— 函数、变量或类型的名字没有揭示它做什么、存什么。→ 重命名；若想不出诚实的名字，说明设计本身模糊。
- **重复代码（Duplicated Code）** —— 同一段逻辑形状在该变更的多个 hunk 或文件中出现。→ 提取共享形状，由两侧共同调用。
- **依恋情结（Feature Envy）** —— 一个方法读取别的对象的数据比读取自身还多。→ 把方法移到它艳羡的数据上。
- **数据泥团（Data Clumps）** —— 同样的几个字段或参数总是结伴出行（一个渴望诞生的类型）。→ 把它们打包成一个类型，传递该类型。
- **基本类型偏执（Primitive Obsession）** —— 用基本类型或字符串顶替一个值得拥有专属类型的领域概念。→ 给该概念一个自己的小类型。
- **重复开关（Repeated Switches）** —— 对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 用多态替换，或让两处共用同一张映射表。
- **霰弹式修改（Shotgun Surgery）** —— 一次逻辑变更迫使在 diff 的许多文件里四处编辑。→ 把会一起变化的东西收拢进一个模块。
- **发散式变化（Divergent Change）** —— 一个文件或模块因多个不相关的原因而被编辑。→ 拆分，使每个模块只为一个原因而变。
- **夸夸其谈的未来性（Speculative Generality）** —— 为规格并不存在的需求而添加的抽象、参数或钩子。→ 删除它；内联回去，直到真实需求出现。
- **消息链（Message Chains）** —— 调用方不应依赖的长链 `a.b().c().d()` 导航。→ 把这段游走隐藏到第一个对象上的一个方法后面。
- **中间人（Middle Man）** —— 一个类或函数几乎只是在向前转发委托。→ 删掉它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）** —— 一个子类或实现者忽略或重写了它所继承的大部分内容。→ 放弃继承，改用组合。

**完成标准**：已列出标准来源文件；smell 基线全文可用（在生成 Standards 子智能体时需粘贴其全文，子智能体没有其他渠道获取它）。

### 4. 并行派发两个子智能体

**Standards 子智能体提示词** —— 包含：

- 完整的 diff 命令与提交列表。
- 第 3 步找到的标准来源文件列表，**外加第 3 步的 smell 基线全文**——子智能体没有其他渠道获取它。
- 交付要点："按相关文件/hunk 汇报——(a) diff 中每一处违反已文档化标准的地方：引用该标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味：点名并引用该 hunk。区分硬违规与判断：违反文档化标准可能是硬违规，但基线坏味始终是判断，且已文档化的仓库标准优先于基线。跳过工具链已强制检查的内容。全文 400 词以内。"

**Spec 子智能体提示词** —— 包含：

- diff 命令与提交列表。
- 规格的路径或已获取的内容。
- 交付要点："汇报：(a) 规格要求但缺失或不完整的部分；(b) diff 中规格并未要求的行为（范围蔓延）；(c) 看起来已实现但实现方式不对的要求。每条发现都引用规格的对应原文。全文 400 词以内。"

若规格缺失，跳过 Spec 子智能体并在最终报告中注明。

**完成标准**：两个子智能体均收到自足的提示词（含 diff 命令、提交列表、各自轴线所需的完整材料与交付要点）；两轴结果均已返回；若规格缺失则已记录跳过结论。

### 5. 汇总

在两轴报告上分别加上 `## Standards` 与 `## Spec` 标题呈现，可原样或略作整理。**不要**合并或重新排序发现——两条轴刻意分开（见 _为何要双轴_）。

结尾给出一行总结：各轴的发现总数，以及**各轴内部**最严重的问题（若有）。不要跨轴挑选唯一赢家——那正是这种分离所要防止的重排序。

**完成标准**：两轴报告在天标题下单独呈现；结尾一行总结含各轴总数与各轴最严重问题；未做跨轴合并或重排序。

## 为何要双轴

一处变更可能过了一轴却栽在另一轴：

- 遵循了所有标准却实现了错误的事情 → **Standards 通过，Spec 失败。**
- 精确实现了 issue 要求却破坏了项目惯例 → **Spec 通过，Standards 失败。**

分开报告能防止一轴掩盖另一轴。
