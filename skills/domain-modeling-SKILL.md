# 领域建模

在设计过程中，主动构建并打磨项目的领域模型。这是一门*主动*的纪律——挑战术语、构造边界场景、并在共识凝结的当下就把词汇表和决策写下来。（仅仅为了查词汇而*读* `CONTEXT.md` 不是本技能，那是一个任何技能都能做的一步习惯。本技能用于你正在*改变*模型、而非仅仅是消费它的时候。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明该仓库有多个上下文，这张映射表指向每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件——只在有内容要写时才创建。若尚不存在 `CONTEXT.md`，在第一个术语得到确认时创建它。若尚不存在 `docs/adr/`，在需要第一条 ADR 时创建它。

## 会话进行中

### 对照词汇表发起挑战

当用户使用了一个与 `CONTEXT.md` 既有语言冲突的术语时，立即指出。「你的词汇表把 'cancellation' 定义为 X，但你现在似乎在说 Y——到底是哪一个？」

### 打磨含糊的语言

当用户使用了含糊或被滥用的术语时，提出一个精确的规范术语。「你在说 'account'——你指的是 Customer 还是 User？它们是不同的东西。」

### 讨论具体场景

当讨论领域关系时，用具体场景对其进行压力测试。构造能探测边界情况的场景，迫使用户精确界定概念之间的边界。

### 与代码交叉核对

当用户陈述某事物如何运作时，核对代码是否一致。若发现矛盾，把它摆到台面上：「你的代码取消的是整个 Order，但你刚才说部分取消是可能的——哪个才是对的？」

### 就地更新 CONTEXT.md

当一个术语得到确认后，立刻就地更新 `CONTEXT.md`。不要攒批——随发生随记录。遵循下面「CONTEXT.md 格式」子节里的格式。

`CONTEXT.md` 应当完全不含实现细节。不要把它当作规格说明、草稿纸或实现决策的仓库。它是一份词汇表，仅此而已。

### 有节制地提议 ADR

只有当以下三条全部成立时，才提议创建 ADR：

1. **难以逆转**——事后改变主意的成本是显著的
2. **缺失上下文会令人惊讶**——未来的读者会疑惑「他们为什么要这样做？」
3. **真实权衡的结果**——确实存在过多个备选方案，而你基于具体理由选择了其中一个

若三条中缺了任何一条，跳过 ADR。遵循下面「ADR 格式」子节里的格式。

## CONTEXT.md 格式

### 结构

```md
# {上下文名称}

{用一两句话说明这个上下文是什么、为什么存在。}

## Language

**Order**:
{用一两句话描述这个术语}
_Avoid_: Purchase, transaction

**Invoice**:
客户在交付后收到的付款请求。
_Avoid_: Bill, payment request

**Customer**:
下单的个人或组织。
_Avoid_: Client, buyer, account
```

### 规则

- **要有主见。** 当同一个概念存在多个词时，挑出最好的那一个，并把其余的列在 `_Avoid_` 下。
- **定义要紧凑。** 最多一到两句话。定义它*是*什么，而不是它*做*什么。
- **只收录本项目上下文特有的术语。** 通用编程概念（超时、错误类型、工具模式）即使项目大量使用它们也不属于这里。添加术语前先问：这是本上下文独有的概念，还是一个通用编程概念？只有前者才收录。
- **在自然簇出现时，把术语归到子标题下。** 如果所有术语都属于同一个内聚领域，平铺列表即可。

### 单上下文 vs 多上下文仓库

**单上下文（多数仓库）：** 仓库根目录下一个 `CONTEXT.md`。

**多上下文：** 根目录的 `CONTEXT-MAP.md` 列出各上下文、它们的位置以及彼此的关系：

```md
# Context Map

## Contexts

- [Ordering](./src/ordering/CONTEXT.md) — 接收并跟踪客户订单
- [Billing](./src/billing/CONTEXT.md) — 生成发票并处理付款
- [Fulfillment](./src/fulfillment/CONTEXT.md) — 管理仓库拣货与发货

## Relationships

- **Ordering → Fulfillment**: Ordering 发出 `OrderPlaced` 事件；Fulfillment 消费它们以开始拣货
- **Fulfillment → Billing**: Fulfillment 发出 `ShipmentDispatched` 事件；Billing 消费它们以生成发票
- **Ordering ↔ Billing**: 共享 `CustomerId` 与 `Money` 的类型
```

据此推断适用哪种结构：

- 若存在 `CONTEXT-MAP.md`，读它来找到各个上下文
- 若只有根目录的 `CONTEXT.md`，则为单上下文
- 若两者都不存在，在第一个术语得到确认时惰性创建根目录的 `CONTEXT.md`

当存在多个上下文时，推断当前话题属于哪一个。若不清楚，就询问。

## ADR 格式

ADR 存放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md`，以此类推。

惰性创建 `docs/adr/` 目录——只在需要第一条 ADR 时才创建。

### 模板

```md
# {决策的简短标题}

{用一到三句话：背景是什么、我们决定了什么、为什么。}
```

仅此而已。一条 ADR 可以只有一个段落。它的价值在于记录*做出了*一个决策以及*为什么*——而不是填满各个栏目。

### 可选栏目

只有当它们能带来真实价值时才加入。多数 ADR 不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策被重新审视时有用
- **Considered Options**——仅当被否决的备选方案值得记住时
- **Consequences**——仅当需要指出非显而易见的下游影响时

### 编号

扫描 `docs/adr/` 中编号最大的一个，加一。

### 何时提议 ADR

以下三条必须全部成立：

1. **难以逆转**——事后改变主意的成本是显著的
2. **缺失上下文会令人惊讶**——未来的读者看着代码会纳闷「他们到底为什么这样做？」
3. **真实权衡的结果**——确实存在过多个备选方案，而你基于具体理由选择了其中一个

如果决策容易逆转，就跳过——你反正会随时逆转它。如果它并不令人惊讶，就没人会疑惑为什么。如果没有真正的备选方案，除了「我们做了显而易见的事」之外就没什么可记录的。

### 什么算得上 ADR

- **架构形态。** 「我们用 monorepo。」「写模型是事件溯源，读模型投影进 Postgres。」
- **上下文之间的集成模式。** 「Ordering 与 Billing 通过领域事件通信，而非同步 HTTP。」
- **带锁定性的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库——只记录那些换掉要花一个季度的。
- **边界与职责范围的决策。** 「Customer 数据由 Customer 上下文拥有；其他上下文仅通过 ID 引用它。」明确的「不做什么」和「做什么」同样有价值。
- **对显而易见路径的有意偏离。** 「我们用手写 SQL 而非 ORM，因为 X。」任何合理的读者都会假设相反做法的东西。这些能阻止下一位工程师「修复」一个本来是有意为之的东西。
- **代码里看不见的约束。** 「我们因合规要求无法使用 AWS。」「由于合作方 API 契约，响应时间必须低于 200ms。」
- **否决理由不明显的被拒备选。** 如果你考虑过 GraphQL 却因微妙理由选了 REST，记录下来——否则六个月后又会有人提议 GraphQL。
