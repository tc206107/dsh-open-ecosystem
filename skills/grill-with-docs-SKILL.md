# 边拷问边写文档（grill-with-docs）

本技能把两件事揉成一次会话：对计划或设计做**层层追问式采访**（压力测试），同时在理解收敛的过程中**就地沉淀文档**——术语进术语表、关键决策进 ADR、需要可复现验证时产出原型。采访是骨架，文档是脊椎；不问一句就凭空写文档，也不只聊天而不留任何可复用的产物。

正面纪律贯穿始终：每个问题都给出推荐答案；每一步都有明确的完成标准；术语一旦定下就全程复用同一个词；不写没有增量价值的段落。

## 会话如何运转

一次会话由两股力量共同驱动。

1. **采访（压力测试）**：把用户的计划或决策映射成一棵**设计树**，按轮驱动 frontier 直到共同理解收敛。这是本技能的推动力。
2. **建模与记录**：在每一轮里，对浮现的术语、决策、边界与原型需求立刻做出反应——挑战、澄清、写文档、出原型。这是本技能的产出。

两者不是先后两个阶段，而是每一轮同时发生：采访的每一轮都可能产出新的术语定义、新的 ADR 或一个新的原型分支。会话完成的标准是两条都收敛：设计树的 frontier 为空（没有静默假设遗留），且所有该落地的文档都已落地。

## 采访：设计树

把用户的计划或设计映射为一棵**设计树**：每个决策都分支出悬挂在它之下的子决策。

按**轮（rounds）**推进。**frontier** 是「前置条件都已解决」的那批决策——即你现在就能问、而不必猜还没听到的答案的问题。每一轮把整个 frontier 一次性问完：给每个问题编号，并给出你的推荐答案。然后等用户回答，再进入下一轮。

每个问题的格式如下：

```
❓ **Q1** - **<问题标题>**：<问题正文，可能多段，包含多个选项>

➡️ <你的推荐答案>
```

每一轮用户的回答都会重塑这棵树——已解决的决策把 frontier 向外推，解锁依赖它们的后续问题。重新计算 frontier，再问下一轮。一个「答案依赖本轮另一个尚未回答的问题」的问题，属于**下一轮**，不属于本轮。

**完成标准**：一轮结束时，把 frontier 显式列出；当 frontier 为空、且用户确认已达成共同理解，压力测试才算完成。在用户确认之前不要动手实现。

## 查事实是你的活，不是用户的

查证 *事实* 是你的职责，永远不是用户的。当某个 frontier 问题需要环境事实（文件系统、工具、代码等），派一个子代理去查——任何你能自己查到的信息都别抛给用户。不要阻塞：一个正在进行的探查只是「未解决的前置条件」，只有依赖它的下游问题需要等子代理回报，其余 frontier 现在就问。

*决策* 是用户的——把每个决策放到他面前并等他定夺。事实和决策分开：事实你查，决策他拍。

**完成标准**：每一个需要环境事实的问题，要么已由子代理查清、要么子代理已在运行且不影响其余问题提问；没有一个「可以自己查却去问用户」的问题。

## 建模：术语表与 ADR

采访进行中，**主动**地构建和打磨项目的领域模型。这是主动纪律——挑战术语、发明边界场景、在术语和决策结晶的那一刻就地写进术语表和决策记录。只是 *读* 术语表找词汇不算本技能；本技能是在你**改变**模型时用的。

### 术语表（CONTEXT.md）

术语表是**术语表，仅此而已**。它绝不承载实现细节，不要把它当规格说明、草稿纸或实现决策的仓库。

目录结构（大多数仓库是单一上下文）：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

若根目录存在 `CONTEXT-MAP.md`，则仓库有多个上下文，map 指向每个上下文的位置；此时系统级 ADR 放在根 `docs/adr/`，各上下文专属 ADR 放在各自的 `docs/adr/`。

**惰性创建文件**——只有在确有内容要写时才建。没有 `CONTEXT.md` 时，在第一个术语被解决时创建；没有 `docs/adr/` 时，在第一条 ADR 需要时创建。

术语表格式：

```md
# {上下文名称}

{一到两句：这个上下文是什么、为何存在。}

## Language

**Order**：
{A 一到两句对术语的描述}
_Avoid_: Purchase, transaction

**Invoice**：
交货后发给客户的付款请求。
_Avoid_: Bill, payment request
```

术语表规则：

- **要有主见。** 多个词指同一概念时，挑最好的那个，其余列进 `_Avoid_`。
- **定义要紧。** 一到两句封顶。定义它**是什么**，不是它**做什么**。
- **只收本上下文独有的术语。** 通用编程概念（超时、错误类型、工具模式）即使被大量使用也不收。加词前先问：这是本上下文独有的概念，还是通用编程概念？只有前者才收。
- **出现自然聚类时用小标题分组。** 若所有术语属于单一内聚领域，平铺即可。

**会话中的建模动作**（每一条都是正面指令，都带完成信号）：

- **对照术语表挑战用词**：当用户用了一个与 `CONTEXT.md` 既有语言冲突的词，当场指出。完成标准：冲突被点明并得到用户裁决。
- **锐化模糊语言**：当用户用了含糊或过载的词，提出一个精确的规范词（「你说的『账号』——是指客户还是用户？这是两码事」）。完成标准：术语收敛为唯一规范词并落入 `_Avoid_` 或正名。
- **用具体场景压测**：在领域关系被讨论时，发明具体场景去戳边界、逼用户说清概念之间的界限。完成标准：边界被精确化并反映到术语表。
- **与代码交叉核对**：当用户陈述「某物如何工作」时，核对代码是否一致；发现矛盾就点出。完成标准：矛盾被解决（改术语或改理解）。
- **就地更新术语表**：术语一旦解决，立刻写进 `CONTEXT.md`，不要攒批。完成标准：术语表在当轮结束前反映最新共识。

### 架构决策记录（ADR）

ADR 放在 `docs/adr/`，用顺序编号：`0001-slug.md`、`0002-slug.md`……。`docs/adr/` 目录惰性创建——在第一条 ADR 需要时才建。

模板：

```md
# {决策的简短标题}

{1-3 句：上下文是什么、我们决定了什么、为什么。}
```

就这些。一条 ADR 可以是单段。价值在于记录「**做了**某个决策」和「**为什么**」——不在于填满小节。

可选小节（只在确有增量价值时才加，大多数 ADR 不需要）：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——决策被重新审视时有用
- **Considered Options**——只有被否掉的可选项值得记住时才写
- **Consequences**——只有非显然的下游影响需要点明时才写

编号：扫描 `docs/adr/` 找最高编号，加一。

**何时提供 ADR**——三条同时成立才提供：

1. **难以逆转**——日后改主意成本显著
2. **脱离上下文会令人费解**——未来读者会想「他们为什么这么做？」
3. **真实权衡的结果**——确有多个可选项，且你为具体理由选了其一

三条缺一就跳过。容易逆转的决策不记（你反正会逆转）；不奇怪的不记（没人会纳闷）；没有真实可选项的不记（除了「我们做了显而易见的事」无可记录）。

典型的够格决策：架构形态（单仓/事件溯源）、上下文之间的集成模式、带锁定成本的技术选型（数据库/消息总线/鉴权/部署目标，不是每个库）、边界与范围决策（显式的「不」和「是」一样有价值）、对显然路径的刻意偏离、代码里看不见的约束、以及拒绝得不显然的备选（否则半年后有人会再提一次）。

**完成标准**：每条浮现的决策都被判定过「要不要 ADR」——要么写了 ADR，要么明确判定三条不成立而跳过；没有一条关键决策静默流失。

## 可复现产物：原型

当采访阶段的某个主题需要「亲自上手按一按、推一推」才能验证——无论是对业务逻辑/状态流转的质疑，还是对界面长什么样的质疑——就地产出可复现原型。原型是压力测试的**替身**：它替用户把「纸面上看起来合理」的东西推到真实用例里，逼出「等等，这不该发生」的瞬间。

先说结论、再选形状：先确认要验证的问题，再决定用哪种原型。**逻辑/状态/数据形状**的问题走逻辑原型；**长什么样**的问题走界面原型；两者都涉及则两个都可，但一次只推进一个明确的问题。

### 逻辑原型

当问题是「这个状态机能否处理 X 然后 Y 的边界」「这个数据模型能否表示某案例」「想先摸清 API 该长什么样」，产出**一个自包含、可邮递分发的 HTML 演示**，让任何人（包括非开发者）点按钮驱动状态模型。它讲领域语言，不讲代码语言。

构建步骤：

1. **先把问题写下来**：在实现前，把「验的是什么状态模型、什么问题」写成一到两句，放在演示顶部的可见引言里（不是注释）。一个答错问题的原型纯属浪费。完成标准：问题被显式写出，事后可核对。
2. **把逻辑隔离成可移植模块**：真正的逻辑放进单个 `<script>`，写成「以后能整体拎进真实代码库」的小型纯模块。按问题选形状，不是按哪个最好接线：纯 reducer `(state, action) => state`（离散事件 + 单一状态）、显式状态机（「当前合法动作有哪些」本身就是问题时）、对纯数据类型的一组纯函数（无隐式当前状态）、或带清晰方法面的类/模块（逻辑确实保有持续内部状态时）。保持纯：无 DOM、无 `document`、无按钮处理器伸进去。页面调用它，绝不反向。完成标准：纯模块可以脱离页面独立存在并被复用。
3. **搭可分享的 HTML**：单文件、纯 HTML/CSS/JS，无框架无打包器无服务器，双击即开、可以邮件传阅。自上而下：① 标题 + 一句话（可探索的问题）；② **当前状态**面板（标签化字段，不是裸 JSON，每次点击后重渲染）；③ **自由按钮区**（每个动作一个按钮、永远可点，任意顺序探玩）；④ **引导走读**（每个 tab 一个场景：场景的平实描述 + 该场景要按的按钮序列，每个步骤是真实按钮；开始的走读重置到已知初始态）。场景要覆盖别扭的案例——happy path、棘手的边界、本该非法的尝试。界面干净克制：清晰排版、充足留白、一个强调色，不搞动画花样。完成标准：任何人能双击打开、不需要讲解就玩懂模型。
4. **交付**：把文件发给对方或帮他打开。有意思的时刻是「等等，这不该发生/我原以为 X 会不一样」——那正是想法的 bug，也正是原型的目的。想要新动作或新场景就加。完成标准：用户实际跑过原型并给出反馈。
5. **收口**：问题被解答后，先记下答案，再收原型——验证过的 reducer/状态机/函数集拎进真实模块（决策被吸收）；HTML 壳留进一次性分支作为一手来源。完成标准：答案已捕获、逻辑已可移植、壳没混进主分支。

反模式（都写成「不做」的正面指令）：不写测试（需要测试的就不叫原型了）；不接真实数据库（除非问题本就关于持久化）；不泛化（「以后想支持 X」一律不做，一次答一个问题）；不把逻辑与页面糊在一起；不上框架/打包器/服务器；不把 HTML 壳发到生产（页面为手点优化，背后的逻辑模块才值得保留）。

### 界面原型

当问题是「这个页面该长什么样」「提交前想多看几版布局」，在**同一条路由**上生成**若干结构迥异**的变体，用浮动底栏切换。用户翻看、选一个（或从各版偷点东西），其余扔掉。

先声明：给默认为 **3 个变体**（超过 5 个就变成噪音了）；用一行把方案写进原型位置或文件头注释（如「三个设置页变体，用 `?variant=` 切换，挂在现有 `/settings` 路由上」）。

**两个子形态——强烈优先子形态 A**：当有现成页面可挂时，把变体渲染在**同一路由**上，用 `?variant=` 参数门控，保留现有数据获取/参数/鉴权，只换渲染子树（这是默认）。只有当原型确实没有可嵌入的页面时才落到子形态 B——新建一次性路由，遵循项目既有路由约定，名字显然带 `prototype`，同样用 `?variant=`。空路由会掩盖满页面才会暴露的设计问题，所以选 B 前先自查「真没有能嵌进去的页面吗」。

变体生成纪律：

- 每个变体守住：页面的目的与可得数据、项目的组件库/样式系统、明确的导出组件名（`VariantA`、`VariantB`、`VariantC`）。
- **必须结构不同**——不同布局、不同信息层级、不同首要可操作项，不是换色或换文案。两张草稿太像就重做一张，并明确「不许用卡片网格」。
- 变体之间**少共享代码**：共享 `<Header>` 可以，共享 `<Layout>` 违背初衷——每个变体都要能自由丢布局。

切换器（浮动底栏，底部居中，三件套）：

- **左箭头**循环到上一个变体（回卷）、**当前变体标签**（显示键名及导出名，如 `B — Sidebar layout`）、**右箭头**循环前进（回卷）。
- 点箭头更新 URL search param（用框架路由），保证可分享、刷新不丢状态。
- 键盘 `←`/`→` 也循环，但焦点在 `<input>`/`<textarea>`/`[contenteditable]` 内时不拦截。
- 视觉上与页面区分开（高对比胶囊 + 轻阴影），明显不是在评审的设计本身。
- **生产构建隐藏**：用环境判断门控，防止原型合并意外把底栏发上海外用户。切换器放共享组件里，两个子形态复用。

收口：某个变体胜出后，先记下答案（哪个变体、为什么），再把胜者折进真实代码、把败者与切换器清出主分支（完整变体集是首要来源，落一次性分支；留在主分支会快速腐烂并误导下一位读者）。子形态 A 折胜者进现有页面、删败者与切换器；子形态 B 把胜者变体晋升为真路由、删一次性路由与切换器。

反模式：只有改色/改文案的「变体」不是变体；把变体接到真实 mutation（只读原型即可，需变更就指向 stub）；把原型代码直接晋升生产（原型约束下写的代码要按规范重写再折入）。

**完成标准**：用户看过多个结构迥异的变体并选出方向；胜者已落主分支、其余已清出；切换器未漏进生产。

## 汇报：交互式架构报告的要点

当会话需要把「哪儿浅、哪儿漏、哪儿该加深」的结论交出去评审时，产出一份报告。报告本身以图形为重、文字极简，全部用本技能的术语（模块、接口、实现、深度、深/浅、接缝、适配器、杠杆、局部性）。**报告要点**如下（本技能只要求说清产出要点，不要求还原完整页面脚手架）：

- **单份自包含文件**，落在系统临时目录；图用 Mermaid（依赖/调用流的结构图）与手搭的框线/内联 SVG（大块图、剖面图）**混合**——别全靠 Mermaid，否则千篇一律。
- **头部**：仓库名、日期、图例（实框 = 模块，虚线 = 接缝，红箭头 = 泄漏，粗深色框 = 深模块）。不写引言段，直接进入候选区。
- **候选卡片**= 一个 `<article>`：标题（短，点名「加深」动作）、徽章行（推荐强度 + 依赖类别标签）、文件清单（等宽）、**before/after 图**（并排，重心所在）、问题一句、方案一句、**Win 要点**（每条 ≤6 词，如「测试只打一个接口」「定价逻辑停止泄漏」）、适用时的 ADR 提示行（琥珀框一行）。不要解释段——图若要一段话才讲清，就重画图。
- **五类图型按需取用**：Mermaid 流程图/时序（依赖与调用流）、手搭框线（想要「一个粗边深模块 + 灰化内部」的感觉时 Mermaid 表现不对）、横带剖面（分层浅薄）、块构图（「接口和实现一样宽」的浅 vs 「接口窄实现厚」的深）、调用图坍缩（把 before 的调用树收进 after 的一个框，内部调用淡显其中）。
- **顶部推荐区**：一张更大的卡，候选名 + 一句理由 + 锚点链接，仅此而已。
- **用词纪律**：只准用 模块/接口/实现/深度（深/浅）/接缝/适配器/杠杆/局部性；禁止用 组件/服务/单元（替「模块」）、API/签名（替「接口」）、边界（替「接缝」）、层/包装器（替「模块」）。Win 要点用术语命名收益（「局部性：bug 集中到一处」「杠杆：一个接口、N 个调用点」），不写「更易维护」「更干净」这类不进术语表的词。不模糊、不清嗓、不写「值得注意的是……」。

## 词汇表（术语必须复用，不得替换）

本技能沿用深模块这一套词汇，全程用同一批词，不发明近义词——一致的语言本身就是目的。

- **模块（Module）**——任何「有接口 + 有实现」的东西，刻意与规模无关：函数、类、包、跨层切片。*Avoid*：单元、组件、服务。
- **接口（Interface）**——调用者正确使用一个模块所需知道的全部：类型签名，外加不变量、顺序约束、错误模式、必需配置、性能特征。*Avoid*：API、签名（太窄，只指类型层表面）。
- **实现（Implementation）**——模块内部、代码本体。与**适配器（Adapter）**区分：小而厚的实现可以是大适配器（Postgres 仓库），大而薄的实现可以是小适配器（内存假实现）。谈接缝时用「适配器」，否则用「实现」。
- **深度（Depth）**——接口处的杠杆：调用者（或测试）每学一单位接口能调动的行为量。模块**深**=大量行为藏在小区接口后；**浅**=接口几乎和实现一样复杂。
- **接缝（Seam）**——能不编辑该处而改变行为的地方；是模块接口**所在的位置**。接缝放哪儿本身是一项独立设计决策。*Avoid*：边界（与 DDD 有界上下文过载）。
- **适配器（Adapter）**——在接缝处满足接口的具体事物。描述的是**角色**（填哪个槽），不是实质（内部是什么）。
- **杠杆（Leverage）**——调用者从深度获得的收益：每学一单位接口换得更多能力。一份实现回馈 N 个调用点和 M 个测试。
- **局部性（Locality）**——维护者从深度获得的收益：变更、bug、知识与验证集中到一处，而非散落各处调用者。改一次，处处修好。

**深 vs 浅**：深模块 = 小接口 + 多实现；浅模块 = 大接口 + 少实现（应避免）。设计接口时自问：能减少方法数吗？能简化参数吗？能把更多复杂度藏进去吗？

**原则**：

- 深度是**接口**的性质，不是实现的：深模块内部可由若干小而可 mock、可替换的部分组成，它们只是不属于接口。一个模块可以既有**内部接缝**（对实现私有、供自身测试）又有接口处的**外部接缝**。
- **删除测试**：想象删掉这个模块。若复杂度随之消失，它就是传声筒；若复杂度在 N 个调用点重新浮现，它就在挣口粮。
- **接口是测试面**：调用者和测试跨同一接缝。若你想测试「接口之后」的东西，模块十有八九形状错了。
- **一个适配器 = 假想接缝，两个适配器 = 真接缝**：除非确实有东西在接缝处变化，否则别引入接缝。

**测试友好设计**：接受依赖而不自建依赖（`processOrder(order, gateway)` 而非内部 `new`）；返回结果而非制造副作用（`calculateDiscount(cart): Discount` 而非 `applyDiscount(cart): void`）；小表面积（少方法 = 少测试）。

## 加深：把一个浅模块簇安全地加深

当采访中发现一个「浅模块簇」值得加深为深模块时，先按依赖类别判定，再决定怎么测。

**依赖四类**：

1. **进程内**：纯计算、内存态、无 I/O。**总可加深**——合并模块、直接经新接口测试，无需适配器。
2. **本地可替换**：有本地测试替身（PGLite 替 Postgres、内存文件系统）。替身存在即可加深；测试时替身在套件里跑，接缝是内部的，模块外部接口无需端口。
3. **远程但自有（端口与适配器）**：跨网络边界是你自己的服务。在接缝处定义**端口**（接口），深模块持有逻辑，传输以**适配器**注入；测试用内存适配器，生产用 HTTP/gRPC/队列适配器。推荐口径：「在接缝处定义端口，生产实现 HTTP 适配器、测试实现内存适配器，这样即使跨网络部署，逻辑仍聚在一个深模块里。」
4. **真正外部（Mock）**：第三方服务（Stripe、Twilio 等）不归你控。深模块把外部依赖作为注入端口接收；测试提供 mock 适配器。

**接缝纪律**：一个适配器 = 假想接缝，两个 = 真接缝；没有至少两个适配器（通常生产 + 测试）就不引入端口——单适配器接缝只是间接层。内部接缝与外部接缝区分：别因为测试用到了内部接缝就把它暴露到接口上。

**测试策略——替换，不叠加**：浅模块上的旧单测在新接口测试存在后即失效——删掉；在深模块接口处写新测试，**接口即测试面**；断言经接口的可观察结果，不测内部状态；测试要能在内部重构后存活——它描述行为而非实现，一旦实现变了测试就变，说明它在测接口之后的东西。

## 设计两次：并行探索可替代接口

当用户想探索某个待加深候选的多种接口形态时，用并行子代理模式。基于「设计两次」（Ousterhout）——你的第一个想法大概率不是最好的。

**三步**：

1. **框定问题空间**：派子代理前，先写一段面向用户的问题空间说明——新接口需满足的约束、依赖什么及其类别、一段粗略示意代码（只为让约束具体，**不是提案**）。展示给用户后**立即进入第 2 步**，用户边读边想、子代理并行工作。
2. **并行派 ≥3 个子代理**，每个产出**迥然不同**的接口。每个子代理发一个独立技术简报（文件路径、耦合细节、依赖类别、接缝背后是什么），各给不同设计约束：「接口最小化——1-3 个入口封顶，每个入口杠杆最大化」/「灵活性最大化——撑住多用例与扩展」/「为最常见调用方优化——默认情形零成本」/ 适用时「围绕端口与适配器设计跨接缝依赖」。简报里同时带上深模块词汇与术语表词汇，让各子代理命名一致。每个子代理输出：① 接口（类型、方法、参数 + 不变量、顺序、错误模式）② 用法示例 ③ 实现在接缝后隐藏什么 ④ 依赖策略与适配器 ⑤ 权衡（杠杆高处和薄处）。
3. **逐个呈现并比较**：按顺序呈现各设计让用户消化，再用散文对比——按**深度**（接口处杠杆）、**局部性**（变更集中处）、**接缝摆放**三轴。比完给出你自己的推荐：哪个最强、为什么；若有来自不同设计的可组合元素就提一个混合方案。要有主见——用户要的是强判断，不是菜单。

**完成标准**：≥3 个结构上真正不同的接口被并行产出、逐轴比较、并给出带理由的明确推荐。

## 会话结束的完成标准

当且仅当以下全部满足，会话才算结束：

1. 设计树 frontier 为空——每一支都已访问，无静默假设遗留；用户确认达成共同理解。
2. 术语表已反映当轮所有已解决术语，且不掺实现细节。
3. 每个浮现的关键决策都被判定过「是否 ADR」，该记的都记了。
4. 需要的原型已产出、已被用户跑过并给出反馈；逻辑可移植、UI 胜者已折入、一次性产物未混进主分支。
5. 全程复用同一套术语，没有一个该用「模块/接口/接缝/适配器/杠杆/局部性」的地方换成了近义词。
6. 每一步都有可见产出，没有「没有增量价值的空段落」。
