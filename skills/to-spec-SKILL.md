# 把会话沉淀为规格（to-spec）

本技能读取当前会话上下文与代码库理解，直接产出一份规格说明，**不向用户访谈**——只综合已经讨论过的内容。

## 目标与完成标准

- 产出一份一次性成型的规格文档，覆盖问题、方案、用例、实现决策、测试决策、范围外与备注。
- 规格全文复用项目领域术语；触及的模块尊重项目内已有架构决策记录。
- 发布的规格标注为「待智能体执行」，无需二次排期。

## 流程

按以下步骤依次执行，每一步都给出其完成标准。

### 1. 理解代码库现状

若尚未探查，先浏览仓库，掌握当前代码状态。**完成标准**：能明确说出要改动/新增的模块、其现有接口与约束，且规格中不再出现"待确认"式的模糊表述。

书写时：
- 全程复用项目领域术语表词汇。
- 尊重触及区域内的现有架构决策记录（ADR）；如需背离，把新决策写进「实现决策」的架构条目，而非静默改写。

### 2. 划定测试接缝（seam）

勾画将要在此特性上做测试的接缝。**完成标准**：每个测试点都有了确切的接缝位置，且接缝总数尽可能少。

- 优先复用现有接缝，其次才新增；用最高处的接缝。
- 确实需要新接缝时，尽量放在尽可能高的位置。
- 全仓库接缝越少越好，理想数量是**一个**。

**完成标准补充**：把这些接缝与用户确认，确保符合其预期后再进入下一步。

### 3. 套用模板产出规格

用下方模板写出规格，再发布到项目需求追踪处。**完成标准**：模板各节均已填实、无占位残留，且发布动作已完成。

## 规格模板

### ## Problem Statement

用户视角下面临的问题。

### ## Solution

用户视角下的解决方案。

### ## User Stories

一份**足够长**、带编号的用户故事清单，每条的格式为：

`1. 作为 <角色>，我希望 <功能>，以便 <收益>`

示例：
`1. 作为手机银行客户，我希望看到账户余额，以便更好地做出消费决策。`

这份清单必须极其详尽，覆盖该特性的方方面面。

### ## Implementation Decisions

已做出的实现决策列表，可包含：

- 将构建/修改的模块
- 这些模块将被修改的接口
- 开发者的技术澄清
- 架构决策
- 模式（schema）变更
- API 契约
- 具体交互方式

**不要**写具体文件路径或大段代码片段——它们很快会过时。

例外：若某个原型产出的片段（状态机、reducer、schema、类型形态）比文字更精确地编码了某项决策，可把它内联到对应的决策条目下，并简短注明它来自原型。只保留决策密集的关键部分——不是可运行的演示，只是要紧的那几行。

### ## Testing Decisions

已做出的测试决策列表，包含：

- 什么算一个好测试（只测外部行为，不测实现细节）
- 将测试哪些模块
- 测试的既有先例（即代码库中同类型的测试）

### ## Out of Scope

本规格范围之外的事项说明。

### ## Further Notes

关于该特性的其他备注。

## 输出要点

产出规格时注意：

- 正文以简体中文为主，术语若项目约定用英文则沿用英文，保持全文一致。
- 用户故事、实现决策、测试决策用编号或列表呈现，便于逐条追踪与评审。
- 实现决策里只保留"决策信息"，剔除会快速过期的细节（路径、行号、可运行代码），符合正文的例外条款才内联片段。
- 发布到需求追踪处后，把规格标注为「待智能体执行」，不额外做排期分类。
