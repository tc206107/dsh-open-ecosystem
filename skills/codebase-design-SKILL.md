# 代码库设计（Codebase Design）

设计**深模块**：大量行为藏在一个小接口之后，放在干净的接缝处，并可通过该接口测试。无论在哪里设计或重构代码，都用这套语言和原则。目标是给调用者**杠杆（leverage）**、给维护者**局部性（locality）**、给所有人**可测试性**。

## 术语表

精确使用这些术语——不要替换成"组件 component""服务 service""API""边界 boundary"。一致的语言是这套方法的核心。

**模块（Module）**——任何有接口和实现的事物。刻意与规模无关：一个函数、类、包，或横跨多层的一整片。_避免用_：单元（unit）、组件（component）、服务（service）。

**接口（Interface）**——调用者为了正确使用该模块而必须知道的一切：类型签名，也包括不变量、顺序约束、错误模式、必需配置，以及性能特征。_避免用_：API、签名（signature，太窄——它们只指类型层面的表面）。

**实现（Implementation）**——模块内部的东西，它的代码体。区别于**适配器（Adapter）**：一个东西可以是"小适配器 + 大实现"（如 Postgres 仓库），也可以是"大适配器 + 小实现"（如内存假实现）。当话题落在接缝上时用"适配器"，否则用"实现"。

**深度（Depth）**——接口处的杠杆：调用者（或测试）每学一单位接口，所能驱动的行为量。当一个模块有大量行为藏在小接口之后，它是**深的（deep）**；当接口几乎和实现一样复杂时，它是**浅的（shallow）**。

**接缝（Seam）**（Michael Feathers 术语）——一处你可以改变行为却无需编辑该处本身的地方；也就是模块接口所**坐落的位置**。接缝放在哪里本身就是一个设计决策，与接缝背后放什么无关。_避免用_：边界（boundary，与 DDD 的有界上下文混义）。

**适配器（Adapter）**——在接缝处满足某个接口的具体事物。描述的是**角色**（它填哪个槽位），而非实质（它内部是什么）。

**杠杆（Leverage）**——调用者从深度中得到的收益：每学一单位接口，获得更多能力。一份实现，在 N 个调用点和 M 个测试处反复收回成本。

**局部性（Locality）**——维护者从深度中得到的收益：变更、缺陷、知识、验证集中在一处，而不是散布到各个调用者。修一次，处处生效。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│     小接口          │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│    深层实现         │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│        大接口                    │  ← 方法多、参数复杂
├─────────────────────────────────┤
│  薄实现（只是透传）               │
└─────────────────────────────────┘
```

设计接口时，问自己：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏到内部吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块可以在内部由若干小的、可 mock、可替换的部件组成——它们只是不属于接口。一个模块可以有**内部接缝**（对其实现私有，供它自己的测试使用）以及位于接口处的**外部接缝**。
- **删除测试（The deletion test）。** 想象删除这个模块：如果复杂度随之消失，那它只是个透传；如果复杂度在 N 个调用者处重新出现，那它确实在发挥作用。
- **接口即测试面。** 调用者和测试穿过同一个接缝。如果你想测试*越过接口*的东西，那这个模块多半形状不对。
- **一个适配器意味着假想的接缝，两个适配器才是真实的接缝。** 除非确实有东西跨越这条接缝变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，而不是创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 方法越少，需要的测试越少；参数越少，测试搭建越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用者和测试的表面）。
- **深度**是**模块**的一个属性，依据其**接口**来衡量。
- **接缝**是**模块接口**所坐落的位置。
- 一个**适配器**位于**接缝**处并满足该**接口**。
- **深度**为调用者产生**杠杆**、为维护者产生**局部性**。

## 被否定的表述方式

- **把深度当作"实现行数 / 接口行数"的比值**（Ousterhout）：这是在奖励给实现注水。我们改用"深度即杠杆"。
- **把"接口"当作 TypeScript 的 `interface` 关键字或类的公开方法**：太窄——这里的接口包含调用者必须知道的每一个事实。
- **"边界 boundary"**：与 DDD 的有界上下文混义。请说**接缝（seam）**或**接口（interface）**。

## 深化（Deepening）

如何安全地深化一组浅模块，取决于它的依赖。假定你已掌握本 skill 的术语——**模块**、**接口**、**接缝**、**适配器**。

### 依赖分类

评估一个深化候选时，先给它依赖分类。分类决定了这个被深化的模块如何跨接缝测试。

### 1. 进程内（In-process）

纯计算、内存态，无 I/O。**始终可深化**——合并这些模块，直接透过新接口测试即可。不需要适配器。

### 2. 本地可替代（Local-substitutable）

依赖存在本地测试替身（如用 PGLite 替代 Postgres、内存文件系统）。若替身存在，则可深化。被深化的模块在测试套件中用运行中的替身来测试。接缝是内部的；模块外部接口处不需要端口。

### 3. 远程但自有（Ports & Adapters）

跨越网络边界（微服务、内部 API）的自有服务。在接缝处定义一个**端口（port）**（即接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试用内存适配器，生产用 HTTP/gRPC/队列适配器。

推荐表述形状：*"在接缝处定义一个端口，为生产实现一个 HTTP 适配器、为测试实现一个内存适配器，这样逻辑就集中在单个深模块里，即便它跨网络部署。"*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（如 Stripe、Twilio 等）。被深化的模块把外部依赖作为注入的端口接收；测试提供一个 mock 适配器。

### 接缝纪律

- **一个适配器意味着假想的接缝，两个适配器才是真实的接缝。** 除非能证成至少两个适配器（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是层层的间接。
- **内部接缝 vs 外部接缝。** 一个深模块可以有内部接缝（对其实现私有，供它自己的测试使用）以及接口处的外部接缝。不要仅仅因为测试用到了内部接缝，就把它暴露到接口上。

### 测试策略：替换，不叠加

- 一旦深模块接口处的测试存在，针对浅模块的旧单元测试就变成浪费——删除它们。
- 在深模块的接口处写新测试。**接口即测试面**。
- 测试透过接口对可观察的结果断言，而非内部状态。
- 测试应该能在内部重构后存活——它们描述的是**行为**而非实现。如果实现一变测试就得改，那它就是在越过接口测试。

## 设计两次（Design It Twice）

当用户想为一个选定的深化候选探索替代接口时，使用这个并行子智能体模式。源自"Design It Twice"（Ousterhout）——你的第一个想法多半不是最好的。

使用本 skill 的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

### 流程

### 1. 框定问题空间

在派生子智能体之前，先为选定的候选写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它要依赖的东西，以及它们属于哪一类依赖（见上文"依赖分类"）
- 一段粗略的说明性代码草图，用来把约束落到具体处——不是提案，只是让约束变具体的方式

把这份说明展示给用户，然后立即进入第 2 步。用户在子智能体并行工作时阅读思考。

### 2. 派生子智能体

并行派生出 3 个及以上的子智能体。每个都必须为被深化模块产出**截然不同**的接口。

给每个子智能体一份独立的技术简报（文件路径、耦合细节、上文的依赖分类、接缝背后放什么）。这份简报与第 1 步面向用户的问题空间说明相互独立。给每个智能体不同的设计约束：

- 智能体 1："最小化接口——最多 1–3 个入口点。最大化每个入口点的杠杆。"
- 智能体 2："最大化灵活性——支持多种用例和扩展。"
- 智能体 3："为最常见的调用者优化——让默认情形变得平凡。"
- 智能体 4（如适用）："围绕端口与适配器，为跨接缝依赖做设计。"

在简报中同时纳入本 skill 的词汇和项目的领域词汇，让每个子智能体用一致的架构语言和项目领域语言来命名。

每个子智能体输出：

1. 接口（类型、方法、参数——加上不变量、顺序约束、错误模式）
2. 展示调用者如何使用它的示例
3. 实现藏在接缝背后的是什么
4. 依赖策略与适配器（见上文"依赖分类"）
5. 权衡——哪里杠杆高、哪里薄弱

### 3. 呈现并比较

按顺序呈现各个设计，让用户逐个消化，然后用散文对比。对照**深度**（接口处的杠杆）、**局部性**（变更集中在哪里）和**接缝位置**来权衡。

比较之后，给出你自己的推荐：哪个设计最强、为什么。如果不同设计的元素能很好地组合，就提出一个混合方案。要有立场——用户要的是一个有分量的判断，而不是一份菜单。
