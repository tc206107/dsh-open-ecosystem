# 调研（research）

本 skill 的职责是：把「查证一个问题」这件事，从当前会话里拆出去，交给一个在后台运行的调研智能体去做，让我在它阅读查证的同时继续推进手头的工作。

## 任务目标

调研智能体要完成三件事，缺一不可：

1. 对照**一手来源**调查问题。
2. 把调查结论写进**一份** Markdown 文件，每条结论都标注它的来源。
3. 把这份文件存到仓库里**本就有这类笔记**的位置。

## 一手来源优先

只有一手来源才算证据：官方文档、源代码、规范/标准、第一方 API。二手转述（博客总结、他人解读、教程复述）只是线索，不是结论。

对每一条结论都要做到「追到底」：顺着它一直回溯到真正拥有这条事实的来源，而不是停在别人对它的转述上。套不进一手来源的说法，要么继续找、要么在笔记里明确标注「暂未证实」。

## 落地格式（## 笔记格式）

写进同一份 Markdown 文件，正文遵守这些规范：

- 以问题或结论的一句话摘要开头，让读者不看全文就能知道答案。
- 每条事实或结论后面紧跟它的来源引用，做到逐条可追溯；引用用「来源：<URL> 或 <文件路径>」的形式标出。
- 结论与证据分开写：先说「结论是什么」，再说「凭什么」。
- 只记查证到的事实与结论，不堆砌过程流水账、不抄录大段原文。
- 文件内不落任何个人信息、机器路径或密钥；遇密钥或隐私数据立即停止并报告，绝不写入笔记。

## 存放位置（## 落盘约定）

先看仓库里**现在**把调研笔记、设计记录、ADR 这类文档放在哪个目录、用什么命名。找到就用现有的约定，保持一致，不要自创一套。

如果仓库里没有现成约定，就放到一个说得通的位置，并在最终答复里明确说出「写到了哪里、为什么放这」。

## 交付标准

完成与否，按下面逐条检查，全部满足才算完成：

- [ ] 每个问题都有明确结论，或明确标注「未证实」。
- [ ] 每条结论都能回溯到一手来源，引用逐条齐全。
- [ ] 结论全部落进一份 Markdown 文件，格式符合上面的笔记格式。
- [ ] 文件存放在符合仓库约定的位置。
- [ ] 最终答复交代了文件路径与放置理由。

任一条未满足，就继续补全再交付，不提前结束。

## 协作说明

- 让调研在**后台**进行：启动后不要干等它读完，继续推进当前会话里的其他工作，收尾时再收结果。
- 若需要先把结论在会话里对齐（比如涉及关键决策的取舍），优先运行 /grilling skill 做追问收敛；确需把过程交接给下一个会话时，运行 /handoff skill 生成交接文档。
- 其余诊断或评审类纪律，在确有需要时分别按 /diagnosing-bugs、/code-review skill 执行，不默认叠加到调研流程里。
