# Ask Matt

你不必记住每个技能，问问就好。

**流程**是一条穿过若干技能的路径。大多数工作沿一条**主流程**前进，另有两条**入口**汇入这条主流程。其余的是**独立技能**，或运行在其他技能之下的**底层词汇**层。

## 主流程：idea → ship

大多数工作走的路线：你有一个想法，想把它做出来。

1. **/grill-with-docs** —— 通过采访把想法磨尖。只要你在一个**工作目录**里，就从这里开始：它是有状态的，把学到的东西留在 `CONTEXT.md` 和 ADR 里。（没有工作目录？用 `/grill-me`——见「独立技能」。两者都运行同一个 `/grilling` 原语；`grill-with-docs` 是会留下书面记录的那个，只要有仓库可留，它就更优。）
2. **分支——你能在对话里解决每一个问题吗？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、一个你必须亲眼看过的界面），就经由一条原型岔路绕过去，两个方向都用**运行 /handoff skill** 衔接（原型住在自己的目录里，这正是 /handoff 的用途——见「阶段边界」）：
   - 先运行 **/handoff skill** 交接出去，然后对着那个文件开启一个新会话，
   - 运行 **/prototype** 用一次性代码回答这个问题，
   - 再运行 **/handoff skill** 把你学到的东西交接回来，并从最初的想法线程里引用它。
3. **分支——这是一次跨会话的构建吗？**
   - **是** → 运行 **/to-spec**（把线程变成一份规格），再运行 **/to-tickets** 把它拆成一张张**曳光弹**工单，每张都声明自己的**阻塞边（blocking edges）**。在本地追踪器上，就是 `.scratch/<feature>/issues/` 下每张工单一个文件，按「阻塞者先行」手工推进；在真正的追踪器上，阻塞边变成原生阻塞链接，任何阻塞项已完成的工单都可以直接开干——对每张工单启动 **/implement**，并在每张之间**在阶段边界压缩或开启新会话**。每张工单自包含，所以上一张的上下文是可丢弃的。
   - **否** → 就在此时此地、同一个上下文中运行 **/implement**。

   无论哪条路，**/implement** 都通过内部驱动 **/tdd** 来构建每个 issue——一次一个红灯-绿灯切片——收尾时运行 **/code-review**，对 diff 做双轴评审（Standards + Spec），再提交。当只想测试先行地构建一个具体行为、而不要完整规格时，单独使用 **/tdd**；当想从某个固定点评审一个分支或 PR 时，单独使用 **/code-review**。

### 上下文卫生

让步骤 1–3 始终待在**一个不被打断的上下文中**——在 **/to-tickets** 之前不要在阶段边界压缩或开启新会话——这样采访、规格、工单都建立在同一份思考之上。随后每次 **/implement** 都从一个工单全新开始。

上限是**智慧区间（smart zone）**：模型仍能清晰推理的窗口（前沿模型约 15 万 token）。如果一个会话在 **/to-tickets** 之前就逼近它，不要在能力衰减的状态下硬撑——在最近的阶段边界压缩上下文或开启新会话，继续前进（见「阶段边界」）。

## 入口

产生工作、然后汇入主流程的起始情境。

- **bug 和请求堆积** → **/triage**。它让 issue 走过分诊角色，产出**智能体可读（agent-ready）**的 issue，随后由 **/implement** 接手。

  分诊只针对**不是你创建的** issue——bug 报告、进来的功能请求、任何未经加工的东西。**/to-tickets** 产出的工单已经是智能体可读的，所以**不要对它们分诊**。

- **有什么坏了** → **/diagnosing-bugs**。用于那些硬骨头：一眼看不出所以然的 bug、时好时坏的偶发、两个已知良好状态之间悄悄溜进来的回归。它在拿到一个 **tight 反馈环**之前拒绝提出理论——一条已经能在这一个 bug 上变红的命令——然后用回归测试修好它。当真正的发现是「没有一个好的接缝把这个 bug 锁住」时，它的复盘会交接给 **/improve-codebase-architecture**。

- **一个巨大而模糊的工程——绿地项目或大功能构建，大到一次会话装不下** → **/wayfinder**，这里认知负荷最高的流程。当从这到那的路还不清晰时，它在 issue 追踪器上绘制一张由**决策工单（decision tickets）**组成的**共享地图**，一次只解决一张——产出的是**决策，不是交付物**——直到迷雾退去、前路清晰。**/grill-with-docs** 磨尖的是一个会话能装下的想法；wayfinder 用于你装不下的那个——它更慢也更稠密，所以只留给那种情况，绝不用在一个界定良好的功能上。

  当地图清晰后，**它交接，不构建**：在 **/to-spec** 处汇入主流程，把地图上的关联决策坍缩成一份可构建的计划，然后照常走 /to-tickets 和 /implement。把地图直接丢进 /implement 会跳过这次坍缩、把关联细节扔掉——只有当这项工程真的足够小时才直接进 /implement。

## 代码库健康

不是功能工作，是维护。

- **/improve-codebase-architecture** —— 一有空就运行，让代码库始终对智能体友好可操作。它会浮出**深化机会（deepening opportunities）**；挑一个就等于*产生了一个想法*，你可以把它带进主流程的 /grill-with-docs。它是找出候选点的勘测；**/codebase-design**（见下）是你设计那个被选中候选点的工台。

## 底层词汇

两个可被模型调用的参考，运行在其他技能**之下**——各自是其词汇的单一事实来源。当问题出在**词**而不是流程时，直接取用它们；或者让上面的技能把它们拉进来。

- **/domain-modeling** —— 打磨项目的*领域*语言：挑战一个模糊术语、解开一个过载词（一个 account 干了三份活）、把一条难以逆转的决策记为 ADR。它是 /grill-with-docs 用来让 `CONTEXT.md` 保持为一份干净术语表的活跃纪律。
- **/codebase-design** —— 设计模块*形状*的深模块词汇（module、interface、depth、seam、adapter、leverage、locality）：在一个干净的接缝处，用一个小接口藏起大量行为。/tdd 和 /improve-codebase-architecture 都说这套语言。

## 阶段边界

**阶段（phase）**是会话内部的一块工作——采访、实现、QA。它故意定义得模糊：当你心想「好了，这件事做完了」时，阶段就结束了。

**阶段边界**是两个阶段之间的缝隙，也是唯一该做这个决定的地方。阶段中间没有决定可做——要么继续，要么把剩下的工作拆给子代理。在阶段中间压缩上下文会让智能体丢掉线索。

### 五种选择

| 选择 | 它做什么 |
| ---- | -------- |
| **继续** | 留在当前会话，完全不切换上下文。 |
| **清空上下文** | 清空上下文窗口，从头开始。 |
| **运行 /handoff skill** | 写一份可移植 Markdown 文件，在任何地方用它开启一个新会话。 |
| **子代理** | 把任务发到它自己的上下文窗口，再取回一份报告。 |
| **压缩上下文** | 压缩当前上下文，用摘要开启一个新会话。 |

### 决策树

在边界处自上而下走。**第一个「是」即为答案。**

**1. 你能在当前会话继续吗？** 两个条件任一成立就是「是」：下一阶段需要把本阶段当作**一手来源**，或者你剩下的智慧区间（约 15 万 token）足以容纳下一阶段。采访 → 实现是标准的「是」：实现要的是推理的原文，不是它的摘要。继续不花成本、不失什么，所以在任何其他选择之前先排除它。

**2. 上下文对接下来的一切都无关吗？** 这个会话里的东西——探索、决策、死胡同——都可丢弃吗？如果是，就**清空上下文**。这是棋盘上最便宜的着法：不花时间，还回整个窗口。清空也不是终点——旧会话仍可恢复。

这里判错的代价是单向的。清掉一份*相关*的上下文，你就丢掉了所建之物的**「为什么」**，再读多少遍 diff 也找不回来。

**3. 你需要交接吗？** 运行 /handoff skill 的适用范围很窄。只有在你换到一个**新的 harness**、搬到一个**新目录**或新仓库、把工作交给一位**同事**、或是在**阶段中间**发现了一个需要分叉又不打断手头工作的支线任务时，才需要它。这个清单就是全部适用条件。运行 /handoff skill 买来的是**可移植性**——一份能移动的文件。如果没有东西要移动，你就不需要它。

**4. 这件事能离手（AFK）完成吗？** 它是否界定得足够紧，以至于你可以离开键盘、无需引导地跑完？那就把它发到一个**子代理**，保持当前会话不动。自动评审是标准用例：智能体读 diff 并回报，它跑的时候你不需要在场。

**5. 否则，压缩上下文。** 上下文相关、同一个 harness、同一个目录，而且你需要留在环内——决策树常常落到这里。给它带一条指令（例如「我们要对这块做 QA」），让摘要在压缩后保留下一阶段所需的内容。

压缩上下文是**默认项，不是首选**。它排在树的最底部，因为上面的四个问题都更便宜或更精确。人们一上来就从这里开始时，失败模式是：一个对某条被摘要压扁的决策「自信地犯错」的新会话。

### 一手来源与二手来源

除了**继续**之外，每一步都把**一手来源**变成**二手来源**——把「原样发生的会话」替换成「关于它的摘要」。这个交易总是同一种形态：

| 来源 | 信息 | 噪声 | 腾挪空间 |
| ---- | ---- | ---- | -------- |
| 一手（继续） | 完整 | 多 | 小 |
| 二手（压缩上下文 / 运行 /handoff skill 交接） | 有损 | 少 | 大 |

这正是问题 1 排在首位的原因。只有当留下比省下的更贵时，你才付这笔「有损」的钱。

### 这些是判断

这些问题不是客观的——每个都有分寸在里面，同一个边界在不同日子里可能走向两个方向。价值在于**按顺序**问它们，在边界处问，而不是在工作中间问。

## 独立技能

完全脱离主流程。

- **/grill-me** —— 和 /grill-with-docs 一样的不留情面的采访，但**无状态**：不落本地、不建 `CONTEXT.md`。当你**不在工作目录里**——磨尖一个计划、一个设计、一篇写作，任何底下没有仓库的东西——取用它。若你在工作目录里，改用 /grill-with-docs：它跑的是同一场采访还留下书面记录，所以是严格更优的那个。
- **/grilling** —— 采访原语本身：轮次、frontier、「事实是智能体的活，决策是你的活」。/grill-me 和 /grill-with-docs 是两条具名入口，/triage、/wayfinder 和 /improve-codebase-architecture 都在内部运行它。只有当你想要不带任何包装的采访本身时，才直接取用它。
- **/resolving-merge-conflicts** —— 逐 hunk 地处理一个进行中的 merge 或 rebase 冲突，按**意图**解决、而意图要追溯到每一边的一手来源，而不是挑行；然后完成这次操作。它绝不跑 `--abort`。独立于所有流程：当你已经身处冲突之中时取用它。
- **/prototype** —— 一个回答单个设计问题的小型一次性程序：这个状态模型感觉对吗，或者这个界面该长什么样。「一次性」是对代码写法的一种约束，不是销毁它的承诺：答案折回真正的代码里，原型本身则作为一份**一手来源**保留在主干外的 `prototype/<name>` 分支上，并从实现 issue 里指向它。它是主流程第 2 步的岔路，但任何时候一个设计问题在纸面上难以定夺时都可取用。
- **/research** —— 把阅读跑腿活委托给一个**后台智能体**：它对照**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你继续干活。它产出的文件是要带**进**主流程、在 /grill-with-docs 处使用的东西——research 喂养思考，而不取代思考。
- **/to-questionnaire** —— 当卡住你的东西不在你脑子里、也不在代码库里，而在**别人脑子里**时，它替你写一份问卷让那人填。它是 /grill-me 的逆过程：它采访的不是你对主题的看法，而是这次**发送**——发给谁、你要拿回什么——并把问题对准那个缺口。拿回来的东西是 /grill-with-docs 或 /to-spec 的素材。
- **/wizard** —— 用于只有**人**才能做的步骤：开通基础设施、设置凭据或 CI 密钥、在一个陌生的第三方控制台里点来点去、跑一次一次性迁移或切换。它生成一个交互式脚本，打开每个 URL、捕获每个值并把它写进 `.env` 和密钥库——于是这套流程不再是你每次都要向智能体重新解释一遍的东西。它是模型可调用的，所以智能体一撞上只有你才能翻越的墙，就会去取用它。如果智能体自己就能干，它就该自己干；这是给「确实需要人在环内」的场景用的。
- **/wait-what** —— 对一条没接住的回复的纠偏。在对话中途、在任意其他技能内部使用它，智能体就会用你缺的上下文、以直白的话、用 `CONTEXT.md` 的词汇重说它刚说过的东西。它是事后补救；/grill-with-docs 是事前解药，因为早早约定好的共享语言才是一开始就拦住行话的根本。
- **/teach** —— 跨多个会话学一个概念，把当前目录当作有状态的工作区。
- **/writing-for-agents** —— 写给智能体读的文档的参考：skill、AGENTS.md、被指向的文档。
