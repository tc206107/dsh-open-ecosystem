# 拆工单（To Tickets）

把一份计划、规格说明或对话拆成一组**工单（ticket）**——每张都是一条「曳光弹」垂直切片，并且明确声明**阻塞它**的其他工单。

工单跟踪器和分类（triage）标签词汇表应当已在会话中提供；如果没有，先运行 `/setup-matt-pocock-skills` 完成配置（如无此技能，则先与用户确认跟踪器类型与可用标签词汇）。

## 流程

### 1. 收集上下文

优先基于对话里已有的内容工作。若用户以参数形式给了引用（规格文档路径、issue 编号或 URL），先取回并完整阅读其正文与评论。

**完成标准**：已掌握全部拆分依据（计划/规格原文 + 引用内容的正文与评论）。

### 2. 探索代码库（可选）

若尚未探索过代码库，先了解代码当前状态。工单标题与描述应使用项目领域词汇表（glossary）的术语，并遵守所涉及区域已有的架构决策记录（ADR）。

寻找「预重构」机会，让实现更容易——「先让改动变得容易，再做那个容易的改动」。

**完成标准**：已能用项目领域术语命名；已发现并记录任何值得前置的重构。

### 3. 起草垂直切片

把工作拆成**曳光弹**工单。

## 垂直切片规则

- 每片切出一条**窄但完整**的路径，贯穿每一层（schema、API、UI、测试）——是垂直切片，而非只切某一层的水平切片。
- 一片完成后可**独立演示或验证**。
- 每片大小应能塞进**单个全新上下文窗口**。
- 任何预重构都应放在最前面。

## 阻塞依赖（blocking edges）

给每张工单标注它**被谁阻塞**——即必须先完成、它才能开工的其他工单。没有任何阻塞的工单可立即开工。

## 宽幅重构（例外情况）

**宽幅重构是垂直切片的例外。** 所谓**宽幅重构**，指某一种机械式改动——重命名一列、改变一个共享符号的类型——其**爆炸半径**波及整个代码库，单次改动会同时打破成千上万处调用点，任何垂直切片都无法独立绿灯落地。不要硬把它塞进曳光弹，而应排成 **expand–contract（扩展–收缩）** 序列：

- 先 **expand（扩展）**：在旧形式旁新增新形式，保证什么都不破坏。
- 再按爆炸半径分**批次**迁移调用点（按包、按目录），每批一张工单、都被 expand 阻塞；因为旧形式仍在，可做到**批与批之间 CI 保持绿灯**。
- 最后 **contract（收缩）**：当不再有任何调用方时删除旧形式，作为一张被所有迁移批次阻塞的工单。
- 当连批次都无法各自保绿时，保留该序列，但让它们共享一条集成分支，全部阻塞一张「最终集成并验证」工单——只有在那里才承诺绿灯。

**完成标准**：每张工单都有垂直切片（或宽幅重构序列）定义、明确的阻塞依赖，且无阻塞工单可立即开工。

### 4. 向用户确认拆分

把提议的拆分以编号列表呈现。每张工单展示：

- **标题**：简短描述性名称
- **被谁阻塞**：必须先完成的其他工单（如有）
- **交付什么**：这张工单打通**端到端**能用的行为

向用户提问：

- 粒度合适吗？（太粗 / 太细）
- 阻塞依赖正确吗——每张工单是否只依赖真正卡住它的工单？
- 有没有工单需要合并或进一步拆分？

反复迭代，直到用户批准该拆分。

**完成标准**：用户已明确批准整份拆分方案。

### 5. 发布工单到配置好的跟踪器

发布已批准的工单。**如何发布**取决于配置的跟踪器——工单本身是一样的，只有阻塞依赖的「形态」不同：

- **本地文件** → 每张工单写一个文件到 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，从 `01` 起**按依赖顺序**编号（阻塞者在前）。每个文件的「被谁阻塞」列出它所依赖的编号/标题。用下面的「本地工单模板」——**一单一个文件**，绝不要合并成单个文件。
- **真实工单跟踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞者在前）逐单发布，使每张工单的阻塞依赖能引用真实的标识符。平台有原生「阻塞/子任务」关系就用它；否则把每张工单的「被谁阻塞」设为阻塞它的那些工单。除非另有指示，应用 `ready-for-agent` 分类标签——工单生来就可被智能体领取。

按**前沿（frontier）**推进：即「所有阻塞项都已完成」的工单。对纯线性链，就是自上而下。

**不要**关闭或修改任何父级 issue。

## 本地工单模板

```
# <NN> — <工单标题>

**要构建什么：** 本工单要打通、从用户视角可见的端到端行为——不是逐层罗列的实现清单。

**被谁阻塞：** 阻塞本工单的编号/标题，或「无——可立即开工」。

**状态：** ready-for-agent

- [ ] 验收标准 1
- [ ] 验收标准 2
```

## 发布到真实跟踪器的工单模板

```
## 父级

指向跟踪器上父级 issue 的引用（若源头是已有 issue；否则省略本节）。

## 要构建什么

本工单要打通、从用户视角可见的端到端行为——不是逐层的实现清单。

## 验收标准

- [ ] 标准 1
- [ ] 标准 2

## 被谁阻塞

- 指向每张阻塞工单的引用，或「无——可立即开工」。
```

无论哪种形式：

- **避免写具体文件路径或代码片段**——它们很快过时。
- **例外**：若某个原型产出的代码片段比散文更精确地固化了某个决策（状态机、reducer、schema、类型形状），就内联它，并简短注明它来自原型。**只截取决策密集的部分**——不是可运行的演示，只是关键片段。

**完成标准**：所有已批准工单均已按依赖顺序发布；每张工单的阻塞依赖与验收标准均可追溯；未改动任何父级 issue。
